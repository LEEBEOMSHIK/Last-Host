# 현행 루프 엔지니어링·하네스 독립 감사

## 감사 결론

현행 루프는 **역할 분리와 완료 추적에는 강하지만, 결함을 처음부터 정확히 정의하고 가장 싼 검증으로 먼저 탈락시키는 구조에는 약하다.** 이번 쥐·오브젝트 가림 작업에서 작업 패킷, 구현 담당, 독립 QA, 총괄 판정은 실제로 적용됐다. 문제는 루프 미적용이 아니라 다음 네 가지다.

1. 첫 교정 작업의 검증 기준이 사용자가 본 `최종 합성 화면의 실루엣 관통`이 아니라 `collider 비중첩·sorting order·접지점`에 맞춰졌다.
2. 새 상태형 런타임 컴포넌트를 씬/통합 담당이 먼저 만들고, 런타임 소유자가 나중에 리뷰했다.
3. 수용 기준과 상태 전이표가 구현 전에 고정되지 않아 QA 실패 때마다 새 계약과 새 테스트가 추가됐다.
4. 변경 뒤 무엇이 무효가 되는지, 언제 전체 회귀를 다시 돌리는지, 같은 계약에서 몇 번 실패하면 패치 누적을 멈출지 정한 규칙이 없다.

따라서 에이전트 수를 더 늘리는 것은 해결책이 아니다. **최종 독립 QA와 총괄 게이트는 유지하되, 구현 전 원증상 오라클·단일 소유자·fail-fast·검증 무효화·중단 규칙을 추가하고 중복 문서를 줄여야 한다.**

## 작업 규모와 비용 판단

이번 문제는 화면상으로는 단순 겹침처럼 보이지만, 최종 선택된 해법은 작은 수치 수정이 아니었다.

- 쥐 가시 폭은 약 `1.86 world`, 오브젝트는 그보다 좁고, 쥐는 긴 꼬리를 포함한 단일 `SpriteRenderer`였다.
- collider만 넓히면 이동 간격이 과도해지고, sorting order만 바꾸면 쥐 전체가 물체 위에 올라온 것처럼 보인다.
- 최종 변경에는 새 `VisualOcclusionResolver2D` 약 348줄, 방향별 collider 동기화, 직렬화 복원, 다중 오클루더 상태, 2px hysteresis, 씬 재생성과 약 231줄의 테스트 변경이 포함됐다.

따라서 최종 구현 자체는 `중위험 상태 전이 수정`으로 보는 것이 맞고 독립 QA가 필요한 수준이다. 다만 **그 수준을 초기에 판정하지 못하고, 1차 교정에서 잘못된 오라클로 통과시킨 뒤 두 번째 전체 루프를 열었으며, 두 번째 루프 안에서도 계약을 세 번 확장한 비용은 과도했다.** 저장소에는 실제 토큰 계측값이 없으므로 정확한 토큰 수를 산출할 수는 없지만, 반복을 만든 사건과 구조 원인은 문서 기록으로 확인된다.

## 이전 교정이 사용자 문제를 놓친 직접 원인

`2026-07-30-production2d-occlusion-hud-correction` 기록은 첫 실패를 명확히 보여준다.

- 사용자 표현은 `벽·통 등의 오브젝트를 넘어다닐 때 앞뒤 표현이 부자연스럽다`였다.
- 구현 전후 스윕에서 collider가 분리돼도 세 대상 모두 `visual overlap`이 있음을 기록했다.
- 그러나 쥐 bounds에 꼬리와 투명 캔버스가 포함된다는 이유로 `visual_overlap=true`를 실패로 판정하지 않았다.
- 완료 기준은 접지점, sorting order, collider와 jitter 중심이었고, 실제 alpha 실루엣이 물체 양쪽에 끊겨 보이지 않는다는 기준은 없었다.
- QA도 `단일 SpriteRenderer라 정밀 마스킹은 제공하지 않는다`, `실제 네이티브 WASD는 미검증`이라고 남기면서도 `완료 가능`으로 판정했다.

즉 검증 에이전트가 부족해서가 아니라 **잘못 정의된 완료 주장에 대해서는 충실하게 검증했지만, 사용자가 실제로 본 화면 결함을 완료 주장에 포함하지 않은 것**이 원인이다. 사용자 피드백이 모호했다면 task에 적힌 지시대로 캡처나 실패 프레임을 요청했어야 했고, 그렇지 않다면 최소한 `최종 합성 화면에서 머리·몸통·꼬리가 분리된 조각으로 보이지 않는다`를 시각 오라클로 잡았어야 했다.

## 두 번째 루프에서 결함이 연속 발견된 이유

두 번째 작업에서는 원증상 기준이 보강됐고 최종 QA도 실제 결함을 잡았다. 다만 발견 순서가 늦었다.

1. 씬/통합 구현 담당이 새 런타임 resolver를 먼저 구현했다.
2. 런타임 담당의 사후 리뷰에서 한쪽 꼬리 조각, 활성 오클루더가 아닌 다른 오클루더로의 hysteresis 누수, 외부 renderer 상태 침범 세 건이 추가로 발견됐다.
3. 독립 QA에서 씬에 직렬화된 `renderer.enabled=false` 복원 실패가 발견됐다.
4. 다음 QA에서 통의 X축 경계에는 2px hysteresis가 적용되지 않아 subpixel 왕복 20회 전환이 발견됐다.
5. 그 수정이 벽의 기존 release 계약을 깨뜨려 다음 QA에서 회귀가 발견됐다.
6. 최초 final 캡처에는 QA 임시 객체가 섞여 CSV의 RatHost 상태와 증거가 불일치했고, final-v2를 다시 생성했다.

이 실패들은 서로 무관한 무작위 버그가 아니다. 모두 `visible ↔ hidden` 상태 머신의 소유권, 직렬화 초기 상태, X/Y 경계, 오클루더 전환, 증거 대상 동일성 문제다. 구현 전에 아래 상태 전이표를 만들었다면 한 번의 표적 테스트 묶음으로 상당 부분을 잡을 수 있었다.

| 상태/경계 | 구현 전 필수 표본 |
| --- | --- |
| 진입 | 좌우 두 조각, 왼쪽 tail-only, 오른쪽 tail-only, 4px 바로 전/후 |
| 유지 | 같은 오클루더 정지, 프레임 변경, flip, X 경계, Y 경계 |
| 해제 | 2px 바로 전/후, 앞/뒤 전환, 짧은 반전 |
| 소유권 | 외부 disabled, resolver가 숨긴 renderer, `OnDisable` 복원 |
| 수명주기 | 씬 저장 당시 hidden, 씬 재로드, Play 진입 첫 프레임 |
| 다중 대상 | A에서 유지, B 신규 진입, A 해제 후 B 진입 |
| 증거 | 실제 RatHost 단일 객체, 임시 QA 객체 없음, CSV와 캡처의 동일 revision·좌표 |

QA가 여러 번 수정 사항을 찾아낸 것은 최종 게이트가 작동했다는 증거이지만, `테스트 수가 많다 = 처음부터 올바른 범위를 검증한다`는 뜻은 아니다. `198/198`, `200/200`, `432/432` 같은 숫자도 원증상과 상태 전이를 오라클로 포함하지 않으면 안전성을 보장하지 않는다.

## 현행 통제 감사

| 통제 | 현재 평가 | 근거와 문제 |
| --- | --- | --- |
| 역할 분리 | 부분 충족 | 구현/QA/총괄 역할은 분리돼 있다. 그러나 새 런타임 `.cs`를 씬/통합 담당이 만들고 런타임 담당이 사후 리뷰해 소유권이 늦게 정해졌다. |
| 독립 QA | 구조상 충족, 인식상 미흡 | 구현자와 QA는 분리됐다. 하지만 QA가 구현 전 원증상 오라클과 상태 전이표를 승인하지 않으며, 구현자가 만든 테스트와 수치 계약을 중심으로 검증할 수 있다. |
| 총괄 게이트 | 충족하나 중복 비용 큼 | 최종 범위·QA 충분성 확인은 유효하다. 반면 모든 작업의 시작과 끝에 반복 호출할 근거가 모호하고, 정형화할 수 있는 초기 risk triage까지 총괄에게 넘긴다. |
| 위험 분류 | 미흡 | `경량`과 `전체`의 이분법뿐이다. 씬 한 파일만 바꿔도 경량에서 탈락해 대부분의 Unity 결함이 같은 최대 루프를 탄다. |
| fail-fast | 누락 | 원증상 재현 실패, 표적 smoke 실패, 첫 QA blocker 발견 시 뒤의 고비용 회귀를 중지한다는 순서가 없다. |
| 변경 무효화 | 누락 | production 코드, 테스트, 씬, builder, Play 상태가 바뀌었을 때 기존 XML·CSV·PNG·Console 결과 중 무엇을 폐기할지 규칙이 없다. |
| 중단/재설계 규칙 | 누락 | 같은 계약에서 패치를 몇 번 반복하면 root-cause/상태표 재검토로 돌아갈지 정해져 있지 않다. |
| 증거 원자성 | 누락 | 캡처 revision, 실제 Root identity, 좌표, resolver 갱신, 임시 객체 유무를 한 묶음으로 기록하는 규칙이 없어 잘못된 final PNG가 생겼다. |
| Unity 세션 소유 | 누락 | QA가 Play 중일 때 다른 담당이 Unity를 조작하지 않았다는 것은 개인 판단으로 지켰지만, task나 게이트의 명시적 lease 규칙이 아니다. |
| 상태 용어 | 모호 | `기술 검증 통과`, `사용자 수용 대기`, `완료`가 분리돼 있지 않아 핵심 UX가 미검증인데도 `완료 가능`이라는 표현이 사용된다. |
| 비용 통제 | 누락 | 위험별 최대 역할 수, 전체 회귀 실행 시점, 반복 실패 횟수, 산출물 최소 단위가 없다. |
| 실행 하네스 | 약함 | 검증 skill과 template은 자유 서술형이며 표준 실행 순서·revision manifest·criteria-to-evidence 매핑이 없다. 많은 `RunCommand`와 CSV가 작업별 임시 절차다. |

## 중복·모호·충돌 규칙

### 중복

- 같은 작업 배정·QA·총괄 5개 게이트가 `AGENTS.md`, `agent-skill-plan.md`, `loop-engineering-gates.md`, 조정자/QA/총괄 역할 파일, `_workspace` 템플릿에 반복된다.
- `task.md`, `work-log.md`, `handoff.md`, `agent-activity.md`, `completion-report.md`가 같은 게이트 상태와 담당 정보를 반복한다.
- 결과적으로 단일 사실 변경에도 여러 문서를 갱신하고 읽어야 하며, 사실성보다 문서 일치 작업에 토큰이 쓰인다.

`docs/agents/loop-engineering-gates.md`를 유일한 실행 규칙으로 두고 다른 문서는 역할 설명과 링크만 유지해야 한다. `task.md`는 계획, `agent-activity.md`는 실제 수행 이력, `verification.md`는 증거, `completion-report.md`는 최종 판정만 소유하도록 중복 필드를 줄이는 것이 적절하다.

### 모호 또는 충돌

- `AGENTS.md`의 경량 루프는 독립 QA·총괄 문서를 생략할 수 있다고 하지만 `loop-engineering-gates.md`는 모든 코드·씬 변경에 이를 필수로 요구한다.
- `agent-skill-plan.md`의 기본 루프는 총괄의 시작 전 검토와 최종 검토를 모두 암시하지만, 총괄 역할 문서는 주요 산출물의 최종 내부 승인에 초점이 있다.
- `승인된 내용만 코드·씬에 반영`과 `이미 승인된 프로토타입 범위 안에서는 구현 가능`의 관계가 명확하지 않아 작은 결함 수정에서도 승인 확인을 반복할 수 있다.
- `독립 검증`은 구현자와 다른 주체라는 뜻만 있고, 어떤 입력을 독립적으로 재구성해야 하는지 정의하지 않는다.
- 실제 네이티브 입력이나 핵심 시각 수용을 남은 위험으로 적어도 기술 완료로 볼 수 있는지 기준이 없다.

## 권장 위험 기반 루프

독립 QA와 최종 총괄 게이트는 유지하되 작업 비용을 다음처럼 차등화한다.

| 등급 | 판정 기준 | 최소 구성과 검증 |
| --- | --- | --- |
| R0 조회 | 파일·상태 조회, 설명, 무변경 | 메인 응답만. 작업 패킷 없음. |
| R1 국소 수정 | 기존 계약 안의 값/문구/국소 코드, 새 runtime 상태·공개 API·에셋·설정 없음, 영향 파일 1~3개 | 구현 담당 1명 → 원증상 표적 검증 → 독립 QA 표적 재검증 → 총괄 최종 판정. 별도 전문 분석, clean clone, 전체 suite는 의존성 근거가 있을 때만. 패킷은 1페이지 요약형. |
| R2 상태/통합 수정 | 새 컴포넌트나 상태 전이, 씬+코드 결합, 물리·정렬·직렬화, 여러 오브젝트, 사용자 가시 결함 | QA가 구현 전 오라클·상태 전이표를 사전 검토 → production 파일별 단일 구현 소유자 → 표적 smoke → 관련 suite → 독립 QA 원증상·경계·회귀 → 최종 전체 suite → 총괄 판정. |
| R3 구조/릴리즈 | 패키지, ProjectSettings, 렌더 파이프라인, 저장 형식, 대규모 아트/씬, 릴리즈 빌드 | 현행 전체 루프와 별도 구조·빌드·회귀 증거 유지. |

이번 최종 resolver 변경은 R2다. 최초의 tieBreak·collider 조정만으로 끝났다면 R1~R2 경계였으나, 새 상태형 컴포넌트가 필요하다고 판단한 시점에 R2로 재분류하고 런타임 담당에게 production 코드 소유권을 넘겼어야 했다.

## 필수 fail-fast 순서

1. **원증상 잠금**: 사용자의 화면·입력·좌표와 같은 실패 증거를 먼저 만든다. 재현하지 못하면 추정 수정하지 않고 질문 또는 `재현 불가`로 중단한다.
2. **완료 주장 한 문장**: 예: `동일 접촉 경로에서 4px 이상 분리된 쥐 alpha 조각이 0건이다.`
3. **QA 사전 오라클 검토**: 구현 코드를 보지 않고 성공·실패·경계·negative control을 표로 승인한다.
4. **단일 ownership 확정**: production 파일마다 구현 소유자 1명을 정한다. 새 runtime `.cs`가 필요하면 씬 담당은 만들지 않고 런타임 담당에게 넘긴다.
5. **한 가설 구현**: 증상과 직접 연결되는 최소 변경만 한다.
6. **표적 smoke**: 원증상, 바로 옆 정상 상태, 한 경계만 검사한다. 실패하면 관련/전체 suite를 돌리지 않고 구현으로 반환한다.
7. **관련 계약 테스트**: 상태 전이표 전부를 실행한다.
8. **독립 QA**: 항상 원증상 재현부터 시작하고, 구현자가 추가한 테스트 통과는 보조 증거로만 쓴다.
9. **전체 회귀**: 표적·관련 검증이 한 revision에서 모두 통과한 뒤 한 번 실행한다.
10. **총괄 최종 판정**: risk, 증거 revision, 미검증 사용자 수용 항목을 확인한다.

## 변경 후 검증 무효화 규칙

다음 문구를 공통 규칙으로 명문화해야 한다.

> 검증 증거는 하나의 verification revision에만 유효하다. production 코드·씬·builder·테스트·Play 상태 중 증거가 의존하는 항목이 바뀌면 해당 증거를 즉시 `무효`로 표시한다. 무효 증거는 최종 통과 수에 합산하지 않는다.

최소 무효화 표:

| 변경 | 반드시 무효가 되는 증거 | 재실행 순서 |
| --- | --- | --- |
| runtime 코드 | 원증상 smoke, 관련 계약, Play 캡처·CSV, Console | 원증상 → 관련 → 최종 full |
| scene/builder/serialized value | 씬 계약, Play 캡처·CSV, scene clean, Console | rebuild/save → 씬 계약 → Play |
| 테스트 코드만 | 해당 suite의 이전 pass count | 테스트 자체 검토 → suite 재실행. production 수정 통과 증거로 단독 사용 금지 |
| QA 임시 객체·좌표·카메라 변경 | 캡처와 그 캡처에 대응하는 CSV | 임시 객체 제거 → 동일 Root/좌표 확인 → 원자 캡처 |
| blocker 수정 | 그 blocker 이후 revision의 모든 고비용 결과 | 표적 회귀부터 재시작. 이전 full suite 재사용 금지 |

`verification.md`에는 `verification revision`, 대상 파일 diff 식별값, 씬, 실제 Root 이름/instance, Play 세션 소유자, 캡처 좌표, 임시 객체 유무를 적어야 한다. 같은 revision이 아닌 XML·CSV·PNG를 한 판정에 섞지 않는다.

## ownership와 Unity 세션 규칙

- 파일 종류가 아니라 **변경되는 불변식**으로 주 담당을 정한다. 상태 머신·renderer 소유권·lifecycle은 게임플레이 구현 담당, 씬 직렬화·배치는 씬/통합 담당이다.
- production 파일 하나에는 한 correction cycle 동안 구현 소유자 한 명만 둔다.
- 담당 범위를 벗어난 새 `.cs` 또는 상태 전이가 필요해지면 수정 전에 task의 위험 등급과 ownership를 갱신한다.
- QA는 production 파일을 직접 고치지 않고 가장 작은 반례를 소유자에게 반환한다.
- Unity Editor/MCP는 한 시점에 한 에이전트만 조작한다. task에 `Unity session owner`를 기록하고, 구현 담당이 Play/compile/저장을 끝내고 넘긴 뒤 QA가 lease를 받는다.
- QA Play 중 다른 담당이 코드·씬을 바꾸거나 Unity 상태를 종료하지 않는다. 변경이 필요하면 QA가 실패 증거를 저장하고 세션을 명시적으로 반납한다.

## 중단 규칙

- QA는 첫 blocker를 찾으면 고비용 전체 matrix/full suite를 중지하고 최소 반례를 반환한다.
- 수정 후에는 무효화된 표적 검증부터 재실행한다. 모든 표적 기준이 한 revision에서 green일 때만 전체 회귀를 한 번 실행한다.
- 같은 수용 기준이 두 correction cycle 연속 실패하거나, QA 중 수용 기준이 두 번째로 확장되면 패치 누적을 중지한다.
- 중지 시 상태를 `수정 필요 — 재분류`로 바꾸고 root-cause, 상태 전이표, ownership, 대안 구조를 다시 검토한다. 실패를 통과 처리하거나 QA·총괄 게이트를 생략하는 의미가 아니다.
- 핵심 사용자 입력·시각 항목을 자동 대체하지 못했으면 상태를 `기술 검증 통과 — 사용자 수용 대기`로 두며 `완료 가능` 또는 `완료`라고 표현하지 않는다.

## 보완 후 기대 효과

- 초기 시각 오라클이 1차 tieBreak/footprint 수정의 불충분함을 전체 회귀 전에 탈락시킨다.
- 새 resolver가 필요해지는 순간 R2와 런타임 소유권이 확정돼 사후 코드 리뷰에서 발견된 세 결함을 구현 단계로 당긴다.
- QA는 첫 blocker에서 멈추므로 `전체 200/201 → 전체 201/202 → 전체 202/202` 반복 대신 표적 회귀 후 마지막 full suite 1회로 줄어든다.
- revision과 원자 캡처 규칙이 임시 QA 객체가 섞인 final 증거를 차단한다.
- 문서의 단일 출처화가 같은 게이트를 여러 파일에 반복 기록하고 읽는 비용을 줄인다.
- 독립 QA와 총괄 최종 승인 강도는 낮아지지 않으며, 오히려 무엇을 검증해야 하는지가 명확해진다.

## 최종 판정

- 현행 루프는 `적용됨`이지만 `비용 효율적·fail-fast한 하네스`로는 불충분하다.
- 이번 반복의 주원인은 에이전트 수 부족이 아니라 **오라클 누락, 늦은 ownership, 변경 무효화 부재, 상태 전이표 부재, 중단 규칙 부재**다.
- 새 역할이나 새 스킬은 필요하지 않다. 기존 조정자·구현 담당·QA·총괄의 순서와 계약을 고치면 된다.
- 최종 독립 QA와 총괄 게이트는 유지하고, 초기 총괄 호출·전문 역할·전체 회귀·문서 산출물만 위험 등급에 맞춰 줄이는 보완이 적절하다.
