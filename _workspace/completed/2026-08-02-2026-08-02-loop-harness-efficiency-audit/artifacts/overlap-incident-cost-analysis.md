# Production2D 가림 교정 사고·비용 독립 감사

## 감사 결론

이번 작업은 단순 collider 수치 조정 수준은 아니었다. 최종 변경에는 방향별 collider 동기화, 프레임별 alpha 계약, 다중 오클루더를 가진 상태형 `VisualOcclusionResolver2D`, 저장 씬 역직렬화 복원, 2px 진입·해제 hysteresis와 회귀 테스트가 포함됐다. 관찰 가능한 변경량은 신규 resolver 약 `348`줄, builder `+67/-4`, side view `+36`, 관련 테스트 `+230/-1`, 씬 직렬화 `+5,669/-5,585`줄이다. 따라서 **중간 규모 런타임·씬 통합 결함 수정**으로 보는 것이 맞다.

그러나 실제 비용은 변경 난이도에 비해 분명히 커졌다. 핵심 원인은 QA 인원이 많아서가 아니라 다음 네 가지다.

1. 직전 작업에서 사용자가 보는 합성 실루엣이 아니라 collider·sorting 수치가 성공 기준이 되어 원 결함이 남았다.
2. 새 상태형 런타임 코드를 씬/통합 담당이 먼저 만들고 게임플레이 담당이 사후 보정하는 역할 역전이 생겼다.
3. 변경 주체가 최소 회귀를 끝내기 전에 독립 QA로 넘겨 `QA 발견 → 구현 보정 → QA 전체 재실행`이 세 번 반복됐다.
4. 관련 테스트 우선 fail-fast가 아니라 매번 전체 EditMode cold run과 대형 매트릭스를 사용했고, 최종 캡처도 비원자적으로 생성해 한 세트를 폐기했다.

토큰 수는 기록에 없으므로 추정하지 않았다. 아래 평가는 Unity 실행 횟수, 에이전트 인계, 테스트·증거 재생성, 산출물 크기처럼 관찰 가능한 대리 지표만 사용한다.

## QA 인원과 역할의 정확한 구분

이번 작업에 기록된 역할은 6종이지만, **독립 QA는 1명/1역할뿐**이다.

| 역할 | 독립 QA 여부 | 실제 책임 |
| --- | --- | --- |
| 메인 조정자 | 아니오 | 작업 패킷·배정·상태 동기화 |
| 비주얼/테크아트 분석자 | 아니오 | alpha·실루엣·가림 계약 수치화 |
| Unity 씬/통합 구현자 | 아니오 | 최초 코드·씬·테스트 구현과 구현자 자체 검증 |
| 게임플레이 런타임 리뷰어/수정자 | 아니오 | 신규 resolver 코드 리뷰와 후속 결함 수정 |
| QA/검증 에이전트 | **예** | 독립 EditMode·MCP·매트릭스·증거 감사 |
| 프로젝트 총괄 관리자 | 아니오 | QA 기록을 근거로 내부 승인 판정; Play 실행자가 아님 |

따라서 “검증 에이전트가 많았는데 왜 못 잡았는가”라는 인상과 기록은 다르다. 구현자 자체 검증, 코드 리뷰, 총괄 검토가 있었지만 독립 검증 실행자는 하나였다. 문제는 숫자가 아니라 **서로 다른 검증 단계의 oracle과 실행 순서**였다.

## 직전 작업에서 현재 사고로 이어진 경위

직전 `2026-07-30-production2d-occlusion-hud-correction`은 다음을 통과시켰다.

- 앞·뒤 위치에서 collider overlap `false`
- 동일 pivot에서 sorting order `+1`
- 스크립트식 물리 접근과 정지 300회 jitter `0`
- 관련 `44/44`, 전체 `198/198`

하지만 같은 검증 문서가 동시에 다음을 명시했다.

- “쥐는 꼬리까지 포함한 단일 SpriteRenderer이므로 몸 일부만 단계적으로 가리는 정밀 마스킹은 제공하지 않는다.”
- 실제 네이티브 WASD는 검증하지 않았다.
- visual bounds overlap은 실패로 판정하지 않았다.

즉 QA가 결함 가능성을 전혀 몰랐던 것이 아니다. **사용자 원문은 ‘오브젝트를 넘어다닐 때 부자연스럽다’였지만 성공 계약은 물리 겹침과 정렬 전환으로 축소됐고, 합성 화면에서 쥐가 여러 조각으로 보이는지는 완료 차단 조건이 아니었다.** 이후 사용자가 실제 화면으로 같은 문제를 다시 제시하면서 현재 작업이 시작됐다. 이는 하네스의 미탐이라기보다 acceptance oracle 불일치이며, 현재 작업 비용 중 상당 부분은 직전 작업의 검증 부채를 상환한 것이다.

근거: 직전 작업의 `verification.md`, `work-log.md`, `agent-activity.md`.

## 관찰 가능한 비용 대리 지표

### 에이전트 인계

- 고유 역할 6종 중 독립 QA는 1종이다.
- 독립 QA 시작 후 `QA → 게임플레이 수정 → QA` 왕복이 **3회** 있었다.
- 최초 구현자가 새 런타임 resolver를 작성한 뒤 게임플레이 담당이 사후 리뷰·수정했으므로, 실제 코드 소유권 인계가 한 번 추가됐다.
- 최종 총괄은 새 결함을 수정하지 않고 승인 기록을 감사했으므로 QA 반복의 원인은 아니다.

### Unity 실행

- 구현자 기록상 EditMode 실행은 최소 **5회**다: `5/8`, `8/8`, `46/46`, `200/200`, 마지막 변경 후 `46/46`.
- 런타임 리뷰 static smoke는 관찰 기록상 최소 **3회**다: tail-only 최초 실패, 좌우 보정 성공, 외부 disabled 성공.
- 독립 QA batch Unity는 **5회 cold process 기동**했다.
  - 첫 실행: 결과 XML 없음, 약 3.99MB 로그, 파일 시각 기준 약 6분.
  - 결과가 있는 전체 EditMode 실행: `200/201`, `201/201`, `201/202`, `202/202`의 **4회**.
  - 네 XML의 실제 테스트 시간 합은 약 `40.1초`지만, 프로세스 기동·임포트 포함 파일 시각 구간은 약 `7분 18초`다. 특히 첫 무효 cold import가 지배적이다.
- 동일 임시 QA 프로젝트를 재사용했지만, 구현 안정화 전에 독립 cold clone 전체 실행을 시작해 이후 전체 재실행이 반복됐다.

### 매트릭스·증거 재생성

- contact CSV: pre-fix, post-fix, final의 **3세대**.
- phase CSV: post-fix, final의 **2세대**.
- stability CSV: post-fix, final의 **2세대**.
- subpixel CSV: post-fix, final의 **2세대**.
- QA 최종 PNG는 4장 1세트를 폐기하고 4장 final-v2를 재생성했다. 구현자 캡처 2장까지 포함해 PNG는 총 `10`개다.
- artifacts 전체는 `34`파일, 약 `18.5MB`다. 이 중 PNG 약 `12.84MB`, 로그 약 `4.81MB`, XML 약 `0.72MB`다.
- 최종 `72 contact + 432 phase`는 종결 증거로는 의미가 있지만, 경계 상태 머신의 핵심 결함은 이 대형 매트릭스보다 뒤의 subpixel/hysteresis 검사에서 발견됐다.

## 필수 비용과 회피 가능 비용

### 필수 또는 합리적인 비용

- 사용자 화면을 기준으로 alpha 실루엣과 물리 footprint를 분리 분석한 비주얼 진단.
- collider-only 조정이 불가능하다는 결론과 새 whole-character occlusion 구조 도입.
- 방향 flip collider, tail-only, renderer ownership, 다중 오클루더, 저장 씬 역직렬화, hysteresis를 다루는 관련 테스트.
- 구현 주체의 자체 검증 1회, 독립 QA 최종 관련/전체 실행 1회, 총괄 승인 1회.
- 사용자 “완벽” 요구에 대응하는 최종 3개 오브젝트·3프레임·앞뒤 합성 증거.
- 실제 WASD·작은 소품 완전 가림을 자동 검증과 구분해 사용자 확인으로 남긴 조치.

### 회피 가능하거나 과도했던 비용

- 직전 작업에서 visual composite acceptance를 생략해 같은 사용자 결함이 재발한 비용.
- 씬/통합 담당이 런타임 상태 머신을 먼저 구현하고 게임플레이 담당이 사후 결함 3건을 고친 이중 소유 비용.
- contract에 이미 있던 tail-only를 최초 테스트에 누락한 비용.
- 독립 QA 준비 전에 save/reload, 객체별 exit axis, 소유권 회귀를 구현 단계에서 끝내지 않은 비용.
- 첫 QA cold clone이 패키지 임포트·Tundra 실패로 XML을 생성하지 못한 무효 실행.
- 모든 코드 수정 뒤 관련 1~10개 테스트부터 실행하지 않고 전체 201/202개 테스트를 네 번 cold run한 비용.
- QA가 Unity 세션을 소유한 상태에서 수정자가 Unity 테스트를 생략하고 다시 QA에 넘겨, QA가 구현자 최소 회귀 역할까지 떠맡은 비용.
- Barrel 수정 후 wall 기존 계약을 실행하지 않아 추가 왕복이 발생한 비용.
- 72/432 매트릭스를 fail-fast 경계 스윕보다 앞서거나 중간 상태에서 생성한 비용.
- 임시 QA 객체가 섞인 비동기 캡처 4장과 CSV를 폐기·재생성한 비용.
- 최종 승인에 쓰이지 않는 pre/post/final 세대 증거를 모두 장기 artifacts로 남긴 비용. 실패 원인 요약과 최종 원본만 보존하고 중간 대용량 로그는 별도 보관할 수 있었다.

## “왜 한 번에 못 잡았는가”에 대한 직접 답

1. **이전 QA는 다른 문제를 검사했다.** 사용자가 보는 조각난 실루엣이 아니라 collider overlap과 sorting order를 통과 기준으로 삼았다.
2. **현재 최초 구현은 계약을 완전히 테스트로 변환하지 못했다.** tail-only는 문서에 있었지만 관련 테스트가 없었다.
3. **상태 머신의 seam 검증이 늦었다.** 저장/재로드, 다중 오클루더, 외부 renderer 소유, X/Y exit axis가 최초 구현자 게이트에 없었다.
4. **대형 매트릭스가 핵심 경계 테스트를 대체했다.** 많은 표본을 돌렸지만 Barrel의 0.001 release는 subpixel 경계 스윕에서야 드러났다.
5. **수정 후 검증 책임이 QA로 넘어갔다.** 변경자가 관련 회귀를 실행하지 않은 채 넘겨 다음 QA가 새 회귀를 처음 발견했다.
6. **증거 생성 자체도 하네스화되지 않았다.** 화면과 CSV를 같은 상태에서 원자적으로 만들지 않아 검증 증거를 다시 만들었다.

즉 “QA가 많아도 무능해서 반복했다”가 아니라, 독립 QA는 한 명이었고 그 한 명이 실제로 세 결함과 잘못된 증거를 차단했다. 다만 그 결함들을 **독립 QA 단계에서 처음 발견하도록 만든 앞단 계약·소유권·fail-fast 하네스가 비효율적**이었다.

## 후속 보완 설계에 반드시 반영할 요구사항

1. 사용자 시각 결함은 수치 계약과 함께 **사용자 화면과 동일한 합성 oracle**을 완료 조건으로 둔다.
2. 상태형 런타임 컴포넌트는 처음부터 게임플레이 구현 담당이 소유하고, 씬/통합 담당은 직렬화·builder·scene wiring만 담당한다.
3. 계약 항목마다 `구현 코드 → 관련 테스트 → Play 증거` 추적표를 두고 tail-only 같은 누락을 구현 인계 전에 검사한다.
4. 독립 QA 전 구현자 fail-fast 순서를 고정한다.
   - 순수 함수/관련 테스트
   - save→reload seam
   - 객체별 entry/release axis와 subpixel 왕복
   - 관련 클래스 전체
   - TechnicalSample2D
   - 전체 EditMode는 구현 안정화 후 1회
5. QA가 결함을 돌려보낸 뒤 코드를 바꾼 주체는 최소 관련 회귀를 직접 통과해야 한다. 그 결과가 없으면 QA 재접수를 금지한다.
6. Unity는 단일 소유 세션으로 운영하되, `QA 세션 반납 → 구현자 최소 검증 → QA 재인수` 상태를 명시한다. “동시 조작 금지”가 “수정자 검증 생략”으로 변하면 안 된다.
7. 독립 cold clone은 최종 후보에서 1회 사용한다. 중간 수정은 warmed 검증 복제본 또는 라이브 관련 테스트로 fail-fast하고, 패키지/Library 준비 상태를 먼저 확인한다.
8. 캡처는 `temp root 0 확인 → 대상 1개 확인 → 상태 설정 → resolver/camera/HUD 동기 갱신 → 즉시 캡처 → 동일 호출의 CSV 기록`을 한 transaction으로 묶는다.
9. 대형 72/432 매트릭스는 최종 종결 증거로 1회만 실행하고, 중간 반복은 실패를 재현하는 최소 등가 클래스만 실행한다.
10. 실패 세대 artifacts는 결함명·핵심 수치·로그 위치만 요약하고, 최종 승인 세대에는 명확한 canonical suffix를 붙여 잘못된 `final` 증거가 남지 않게 한다.

## 최종 판정

- 작업 난이도: **단순 수정 아님 — 중간 규모 상태형 런타임·씬 통합 수정**.
- 비용 적정성: **부분적으로 부적정**. 근본 진단·새 resolver·독립 QA는 필요했지만, 이전 acceptance 누락, 역할 역전, 3회 QA 왕복, 5회 batch 기동, 4회 전체 suite, 캡처 재생성은 구조적으로 줄일 수 있었다.
- QA 수: **독립 QA 1명**. 여러 역할을 QA 인원으로 합산하면 안 된다.
- 반복 수정의 직접 원인: 저장 씬 seam, 객체별 hysteresis 축, 회귀 미실행.
- 반복 수정의 구조 원인: 합성 oracle 부재, 계약→테스트 추적 누락, 변경자 최소 회귀 부재, QA/Unity 세션 인계 규칙 미비, 비원자적 증거 캡처.
- 하네스 보완 우선순위: **변경자 fail-fast 및 검증 무효화 규칙 → Unity 단일 소유 인계 → save/reload·축별 boundary harness → 원자적 캡처 → 최종 1회 cold clone/대형 매트릭스**.
